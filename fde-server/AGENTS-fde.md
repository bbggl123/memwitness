# FDE 工作知识（会议分析 / 需求挖掘 / 报告规范）

# 四维辩证法（精编版 · 供 system prompt 注入）

> 完整方法论见 `materials/skills/socratic-need-digging/`。本文件是注入到 Agent 上下文的精简行动版。

## 目的

从客户表面陈述中区分**真需求**与**表面诉求**。永远不把客户的第一句话当成需求本身。

## 第一步：意图解码

每条客户陈述拆三要素：

| 要素 | 问自己 | 示例 |
|---|---|---|
| 声称痛点 X | 客户明确说了什么问题 | "财务人手不够" |
| 暗示方案 Y | 客户默认的解决方向 | "要加 2 个财务" |
| 模糊标记 | 哪些词没量化（很忙/经常/大概） | "经常出错" |

## 第二步：四维验证（每维 1-5 分，缺信息就标"待追问"）

| 维度 | 核心问题 | 追问模板 |
|---|---|---|
| 强度 Intensity | 痛有多痛？替代方案成本多高？ | "现在怎么解决的？成本多少？""不解决最坏会怎样？" |
| 频率 Frequency | 多久发生一次？会持续吗？ | "周期性还是偶发？""上线后每周用几次？" |
| 范围 Scope | 影响多少角色/部门？ | "哪些团队受影响？""多少用户会遇到？" |
| 价值 Value | 解决后可量化收益是什么？ | "能省多少人力/时间/风险？" |

**评分口径**：1=可接受；3=困扰、替代方案贵；5=不可忍受、无替代方案。高频×高强度×大范围×高价值 → 优先做。

## 第三步：Gap 识别（表面需求 vs 真需求）

| Gap 类型 | 表现 |
|---|---|
| 方案错位 | 要 A，实际需要 B（要加人 → 实际要流程规范） |
| 信息盲区 | 关键数据缺失（不知替代方案成本） |
| 假设错误 | 前提不成立（以为人手不足是主因） |

## 会中使用（入耳提示）

- 触发条件：客户陈述出现模糊标记 / 方案-痛点错位 / 四维中两维以上无信息。
- 提示格式：一句话点出盲区 + 一个最值得问的问题。例："他说的'经常出错'还没量化，可以问每周错几次、集中在哪类单据。"
- 客户已自然追问到的不重复提示；同一话题最多提示 2 次。

## 会后输出

每条需求给出：表面需求 → 真需求假设 → 四维评分（含证据/原话时间戳）→ Gap 类型 → 建议追问或建议方案。

# FDE 需求分析手册（方法论工具箱）

> 与四维辩证法配合使用：四维判断"值不值得做"，本手册判断"怎么定义、排序与验收"。

## 1. KANO 模型（需求分类）

| 类别 | 判断特征 | 策略 |
|---|---|---|
| 基本型（Must-have） | 没有就投诉，有了不感激 | 优先保障，不过度打磨 |
| 期望型（Performance） | 越多越好，可比较 | 按投入产出排序 |
| 兴奋型（Delighter） | 没有没感觉，有了很惊喜 | 资源富余时做，控制数量 |
| 无差异 | 有没有都无所谓 | 不做 |
| 反向 | 做了反而减分 | 明确排除并告知客户 |

追问法：分别问"如果没有它会怎样 / 如果有它会怎样"，两者都不痛 → 无差异型。

## 2. MoSCoW 优先级（范围取舍）

- **Must**：本期不做就不能上线（有明确截止日/合规要求）。
- **Should**：重要但可短期绕过（有 workaround）。
- **Could**：锦上添花，排期富余再做。
- **Won't（本期）**：明确不做并记录原因，防止范围蔓延。

操作：和客户一起把需求清单逐条贴入四栏；Must 数量超过容量时，回到四维评分砍优先级，而不是默默加班。

## 3. 5W2H 需求澄清（追问清单）

| 维度 | 问题 |
|---|---|
| What | 要解决的具体问题是什么？ |
| Why | 为什么现在做？不动会怎样？ |
| Who | 谁用？谁拍板？谁买单？ |
| When | 什么时候要？节奏是？ |
| Where | 在什么场景/渠道使用？ |
| How | 现在怎么解决？期望怎么解决？ |
| How much | 预算、人力、时间上限？ |

会中用法：客户陈述落在哪一栏空白，就优先补哪一栏。

## 4. 用户故事地图（叙事排序）

1. 按用户旅程列主干活动（如：提交报销 → 审核 → 打款）。
2. 每个活动下拆用户故事："作为<角色>，我想<动作>，以便<价值>"。
3. 先排"走路骨架"（端到端最简可用），再排迭代深化；避免按模块竖切导致每期都不可用。

## 5. 真需求 / 伪需求快速判别

伪需求常见信号：
- 只有"要有"没有"为什么要"；
- 频率与强度都说不清；
- 方案先于问题（指定了实现路径）；
- 收益无法量化也无法定性描述；
- 与既有流程/系统强冲突且无人愿改。

处理：不直接否定，转成待验证假设，写入报告并设计最小验证（追问 / 数据 / 试点）。

## 6. 需求卡标准格式（写入报告与记忆库）

```markdown
### 需求点：<一句话标题>
- 表面需求：客户原话（带时间戳）
- 真需求：经四维分析后的结论
- 四维评分：强度x 频率x 范围x 价值x（各附证据）
- KANO 分类 / MoSCoW 优先级
- Gap：方案错位 / 信息盲区 / 假设错误（如有）
- 建议追问 / 建议方案
- 状态：待确认 / 已确认（decided）
```

# 会后需求分析报告格式约定（v1）

> PRD F5：会后 10 分钟内产出；每条需求可溯源到客户原话时间戳；真伪判定与人工标注一致率 ≥80%。

## 1. 报告结构（Markdown）

```markdown
# 需求分析报告：<会议主题>
- 会议时间：YYYY-MM-DD HH:mm–HH:mm
- 参会方：客户侧（角色）/ 我方（角色）
- 记录来源：D3200 录音（转写引擎版本）+ 人工旁听补充
- 生成时间：ISO8601

## 一、会议概要
3-5 句话：谈了什么、结论是什么、遗留什么。

## 二、需求清单（按 MoSCoW 排序）
### 需求点 N：<标题>
- 客户原话："<引用>"（<时间戳>，说话人）
- 真需求判定：<结论>（真需求 / 待验证 / 伪需求）
- JEV 判定：P(真需求)=0.xx，P(模糊)=0.xx（<200ms/条）
- 四维评分：强度x 频率x 范围x 价值x（证据摘要）
- KANO / MoSCoW：类别 / 优先级
- 建议追问 / 建议方案

## 三、真伪判定汇总表
| # | 需求点 | 客户原话时间戳 | 判定 | P(真) | 依据 |

## 四、待澄清问题清单
| # | 问题 | 源自 | 建议提问时机 |

## 五、联网检索依据（anysearch）
每条依据格式：《来源名〉〈URL〉〈引用要点〉〈检索时间〉

## 六、下一步
- 我方承诺（decided）
- 客户承诺（decided）
- 下次会议待确认事项
```

## 2. 溯源规则

- 每条需求至少 1 条原话引用，格式：`"原话"（HH:mm:ss，说话人）`；时间戳来自转写记录。
- 转写中不存在推断来源的表述，必须标 `（分析师推断，基于 HH:mm:ss 陈述）`。
- 判定证据链：原话 → 四维评分 → JEV 概率 → 结论；四者缺一不可。

## 3. 质量红线

- 禁止出现转写与记忆库中不存在的"客户原话"。
- 数字必须与原话一致或标注为估算。
- 报告生成后写入 `reports/YYYY-MM-DD-<会议id>.md`，并 git commit 留痕。
- 同一会议重复生成时，新版本覆盖旧版本前需保留 diff 摘要。
